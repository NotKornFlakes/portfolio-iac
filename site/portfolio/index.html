Deception & Threat Research

Rust Telnet Honeypot: What IoT Botnets Do After Login

A telnet honeypot in Rust on Google Cloud. Its fake shell records what bots do after they log in, and it's built to run nothing they send.

  • Recorded 5,527 connections from 790 IPs in 186 hours (Nov 3–10, 2026). 839 logins sent 3,784 commands, including 23 malware download attempts.
  • 0 outbound connections from the sensor in that window, in both the host and cloud firewall logs: it stayed contained.
  • Mapped the post-login playbook to MITRE ATT&CK: router-menu escapes, BusyBox checks, writable-folder probes and droppers for several CPU types.
  • Reported 170 attacking IPs to AbuseIPDB. At least 316 of the 330 IPs that got into the shell (96%) had been reported before they arrived.
  • Layered so each safeguard still holds if the one before it fails: fixed replies compiled into the program, a noexec systemd sandbox, and outbound traffic denied at both the host and cloud firewalls.

What this shows I can do for you: build something that's safe to leave running on its own, and report what it found in plain numbers.

Detection Rules

Playbook Defense: Honeypot Findings as Alerts, Allowlist and Trap

17 Sigma rules mapped to each step of the IoT botnet playbook, a Google Cloud firewall allowlist in Terraform, and an internal NAS decoy designed so that any connection to it raises an alert.

  • Wrote 17 Sigma rules, with one or more for each of the 12 playbook steps. On each push, CI checks them against MITRE ATT&CK, converts them to Splunk searches and validates the Terraform.
  • Admin ports are set to answer only allowlisted addresses, such as the VPN and Identity-Aware Proxy. Telnet is closed to everyone by default, and IoT devices may reach only approved servers. One file feeds both the firewall and the alerts, so both are built from the same list.
  • The NAS decoy runs the honeypot's fake shell with no public IP. No real person or system is meant to use it, so a connection to it should be a high-confidence alert.
  • Not deployed to a real network yet. The rules have been converted and the Terraform validated in CI, but neither has run against live traffic.

What this shows I can do for you: turn findings into rules and config you can review, test and reuse, and say plainly what's been tested and what hasn't.

Detection & Response

SOC Home Lab: Azure Honeypots + Sentinel

Three internet-facing honeypots feeding Microsoft Sentinel, used to write and test detections against real attack traffic.

  • Deployed Windows RDP, Cowrie SSH and Endlessh honeypots with Azure Monitor Agent and custom log tables. Captured 1.24M attempts from 75 IPs in about 37 hours, and no attacker logged in to a real system.
  • Three IPs made 95% of the attempts, all of them on RDP.
  • Wrote 5 KQL analytics rules (password spray, brute-force-then-success) and rebuilt the low-and-slow rule after v1 missed an attacker guessing once every 12 minutes.
  • Reconstructed an SSH intrusion chain, mapped 13 ATT&CK techniques, and identified Panchan, Mirai and Bashlite samples by hash.

What this shows I can do for you: set up logging and alerts, then fix them when they miss something.

SOAR Automation

Sentinel SOAR: Automated Brute-Force Response

A Logic App playbook that looks up Sentinel incidents in a threat-intel feed and blocks high-risk IPs automatically.

  • Connected Sentinel, the AbuseIPDB API and the Azure REST API, running under a least-privilege managed identity.
  • Automated triage took about 12 seconds on average (8–18 s), against an estimated manual triage time of 10–15 minutes. No further attempts from the 3 blocked IPs reached the VM during the ~62-hour test.
  • Grouping by attacker IP turned 65 alerts into 6 incidents on the first night.
  • Ran in October 2026. All resources were deleted after the test.

What this shows I can do for you: connect the tools you already use so routine steps happen on their own, with only the access they need.

Hardening & Change Control

This Website: Cloudflare + Terraform

The page you're reading is served from Cloudflare's edge, with no separate origin server to bypass, and it's deployed entirely from code.

  • Changes go through a pull request, a reviewed Terraform plan and an approval gate. A GitHub ruleset blocks direct pushes to main, admins included.
  • 21 automated checks verify the live headers, HTTPS, DNSSEC and email records after each deploy, and a weekly run flags drift from the code.
  • Email anti-spoofing (SPF, DKIM, DMARC reject), DNSSEC and a CSP that allows no third parties. Graded A+ by SSL Labs (checked Nov 14, 2026).

What this shows I can do for you: set up email anti-spoofing, security headers and a review step before changes go live, then check them from the outside.
