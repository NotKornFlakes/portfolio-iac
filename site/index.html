Projects

Detection & Response

SOC Home Lab: Azure Honeypots + Sentinel

Problem
I wanted to watch real attacks on internet-facing servers and practice writing alerts that catch them, without letting an attacker reach a real system.
What I built
Three honeypots in Azure (a Windows VM with RDP open, a Cowrie fake SSH shell and an Endlessh tarpit) feeding Microsoft Sentinel through Azure Monitor Agent and a custom log table. Then I wrote 5 KQL detections for what I saw, from password spraying to a brute force followed by a successful login. My own admin access was key-only, on a non-standard port, from one IP.
Tools
Microsoft SentinelKQLAzure Monitor AgentCowrieEndlesshMITRE ATT&CKD3
Result
1.24 million attempts from 75 IPs in about 37 hours, and no attacker got into a real system. Three IPs made 95% of them. I reconstructed an SSH intrusion chain, mapped 13 ATT&CK techniques and identified Panchan, Mirai and Bashlite by file hash. The first low-and-slow rule missed an attacker guessing once every 12 minutes, so I rebuilt it.

SOAR Automation

Sentinel SOAR: Automated Brute-Force Response

Problem
Brute-force alerts come in faster than anyone can triage them by hand. Looking up each attacking IP and deciding whether to block it takes an estimated 10–15 minutes.
What I built
A Logic App that runs when Sentinel opens a brute-force incident. It looks the IP up in AbuseIPDB, writes the result onto the incident and adds high-risk IPs to a firewall deny rule, using a managed identity with only the access it needs. Lower scores are tagged for a person to review.
Tools
Microsoft SentinelKQLLogic AppsAbuseIPDB APIAzure REST APINSGManaged Identity
Result
High-risk IPs were blocked about 12 seconds after their incident opened (8–18 s across 3 incidents), and no further attempts from them reached the VM during the ~62-hour test. Grouping alerts by attacker IP turned 65 alerts into 6 incidents on the first night. It also showed what it missed: 5 of 8 attackers scored below the blocking threshold, and one stayed under the alert threshold for about a day, so I wrote a second rule that would have caught it within two hours.

Deception & Threat Research

Rust Telnet Honeypot: What IoT Botnets Do After Login

Problem
I wanted to record what IoT botnets do after they log in, without giving them anything real to run or reach.
What I built
A telnet honeypot in Rust, run on Google Cloud for 186 hours. Common factory-default logins get into a fake shell where every reply is fixed text compiled into the program. It's contained in layers: a sandboxed systemd service, with outbound traffic denied at both the host and cloud firewalls. A follow-up project, Playbook Defense, turned the findings into 17 Sigma rules and a firewall allowlist in Terraform.
Tools
RustGoogle CloudTerraformnftablesSigmaMITRE ATT&CKpandasPlotly
Result
5,527 connections from 790 IPs (Nov 3–10, 2026). 839 logins sent 3,784 commands, including 23 malware download attempts, and the sensor made 0 outbound connections. The 17 Sigma rules cover all 12 playbook steps and are tested in CI, but haven't run against live traffic yet.

How I work

I use Claude, Anthropic's AI assistant, to build faster. Then I read, test and document everything myself before it goes live.

  • Secure by default. Anything I build gets the least access it needs. Passwords and keys stay out of the code, and data isn't kept longer than the job needs.
  • Reliable. I test with real examples, and anything that runs on its own tells someone when it fails.
  • Reviewed before it ships. Changes go through a pull request and a reviewed plan, and I check the result from outside instead of trusting a green pipeline.
  • Documented for the next person. I write down how things work and what to do when they stop, so nobody's stuck waiting on me.
  • Honest about what's tested. If something has only run in a lab, I say so.
  • Clear handoffs. When something's beyond me, I escalate early, with what I found and what I've already tried.
